# Cache lookup validates storage and self-heals Dangling Cache Entries

Returning a download URL from `GetCacheEntryDownloadURL` is a promise that the data exists: once a client holds the URL it has committed to downloading, and the GHA cache protocol gives it no way to walk a download failure back to a cache miss. `@actions/cache` tolerates a broken promise by retrying 5xx and falling back on 4xx, but BuildKit's `gha` cache importer treats any non-200 on the download URL as a hard build failure. Under ADR-0001 the server never creates a Dangling Cache Entry itself, so a broken promise only arises from external mutation of storage the server owns (bucket wipe, external lifecycle expiry, out-of-sync database restore). We choose to own that drift rather than declare it operator error, because self-hosted object stores, bucket lifecycle rules, and backup restores are the daily reality of this project's users, and the alternative failure mode — a silent hard build break that self-heals only after the 30-day cache-entry cleanup or manual database surgery — is unacceptable for a drop-in cache.

The lookup therefore validates storage before returning a URL, and before taking any Storage Reader Lease (nothing should lease provably-dead data): a merged entry is confirmed by a `HEAD` on its merged object; an unmerged entry by a `HEAD` on its first Part (`parts/0`); an entry whose Parts were deleted with no completed Merge is Dangling with no storage call. A `HEAD` fires only on a cache hit, where it is negligible against the transfer that follows. Checking only the first Part will not detect surgical deletion of an interior Part, but the server's invariants never produce partial Part loss and external drift is folder-level all-or-nothing, so a single `HEAD` is sufficient.

On a failed check the lookup deletes the Dangling `cache_entries` row (and reaps the now-childless `storage_location`, which an Orphaned Storage sweep cannot see) and re-runs matching so a valid candidate under another restore key still wins, bounded to a small retry count to cap a pathological same-prefix stale flood; if no valid match remains it returns `{ ok: false }` for a clean miss. This self-heal deliberately reverses the read-purity choice of #223, which removed read-path deletes: that choice was right when the signal was ambiguous, but here the deleted row is provably dead — its storage was just confirmed absent — so eager reconciliation on read is reconciliation in ADR-0001's own spirit, done at read time instead of by a background sweep, and it avoids re-paying the validation `HEAD` on every future restore of the same dead key.
